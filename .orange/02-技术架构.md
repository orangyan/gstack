# GStack 技术架构详解

## 一、整体架构设计

### 1.1 核心理念

**关键洞察**：AI 代理与浏览器交互需要**亚秒级延迟**和**持久化状态**。

- 如果每个命令都冷启动浏览器 → 每次工具调用等待 3-5 秒
- 如果浏览器在命令之间死亡 → 丢失 cookie、标签页和登录会话

**解决方案**：运行长寿命的 Chromium 守护进程，CLI 通过 localhost HTTP 通信。

### 1.2 架构图

```
Claude Code                     GStack
─────────                      ──────
                               ┌──────────────────────┐
  工具调用: $B snapshot -i     │  CLI (编译的二进制)   │
  ─────────────────────────→   │  • 读取状态文件       │
                               │  • POST /command      │
                               │    到 localhost:PORT  │
                               └──────────┬───────────┘
                                          │ HTTP
                               ┌──────────▼───────────┐
                               │  Server (Bun.serve)   │
                               │  • 分发命令            │
                               │  • 与 Chromium 通信    │
                               │  • 返回纯文本          │
                               └──────────┬───────────┘
                                          │ CDP (Chrome DevTools Protocol)
                               ┌──────────▼───────────┐
                               │  Chromium (headless)  │
                               │  • 持久化标签页        │
                               │  • Cookie 保持        │
                               │  • 30 分钟空闲超时    │
                               └───────────────────────┘
```

**性能**：
- 首次调用启动所有组件：~3 秒
- 后续每次调用：~100-200ms

## 二、技术栈选择

### 2.1 为什么选择 Bun

虽然 Node.js 也能工作，但 Bun 在这里更优，原因有四：

#### 1. **编译的二进制文件**
```bash
bun build --compile → 单个 ~58MB 可执行文件
```
- 运行时无需 `node_modules`
- 无需 `npx`，无需 PATH 配置
- 二进制文件直接运行
- 重要性：gstack 安装到 `~/.claude/skills/`，用户不希望管理 Node.js 项目

#### 2. **原生 SQLite**
- Cookie 解密直接读取 Chromium 的 SQLite cookie 数据库
- Bun 内置 `new Database()` - 无需 `better-sqlite3`
- 无需原生插件编译，无需 gyp
- 减少在不同机器上的故障点

#### 3. **原生 TypeScript**
- 开发时服务器运行为 `bun run server.ts`
- 无编译步骤，无 `ts-node`，无 source map 调试
- 编译的二进制用于部署；源文件用于开发

#### 4. **内置 HTTP 服务器**
```typescript
Bun.serve({
  port: randomPort,
  fetch: handleRequest
})
```
- 快速、简单，无需 Express 或 Fastify
- 服务器总共处理 ~10 个路由
- 框架是多余的

**性能瓶颈分析**：
- 瓶颈始终是 Chromium，而非 CLI 或服务器
- Bun 的启动速度（编译二进制 ~1ms vs Node ~100ms）是加分项，但不是选择理由
- **真正原因**：编译的二进制 + 原生 SQLite

### 2.2 Playwright vs Puppeteer

选择 **Playwright** 作为主要浏览器自动化库：

| 特性 | Playwright | Puppeteer |
|------|-----------|-----------|
| 跨浏览器支持 | Chromium、Firefox、WebKit | 仅 Chromium（core 版本） |
| API 设计 | 现代、自动等待 | 需要手动等待 |
| 开发维护 | Microsoft（活跃） | Google（活跃） |
| CDP 访问 | ✅ 通过 newCDPSession() | ✅ 原生 |

**实际使用**：
- 主要使用 Playwright 的 CDP（Chrome DevTools Protocol）会话
- 利用 Playwright 的页面管理和上下文隔离
- 使用 `puppeteer-core` 作为 CDP 的补充（用于某些高级操作）

### 2.3 其他关键依赖

```json
  "@ngrok/ngrok": "^1.7.0",               // 隧道（pair-agent）
```

## 三、守护进程模型

### 3.1 为什么不是每次命令启动浏览器？

**问题**：
- Playwright 启动 Chromium：~2-3 秒
- QA 会话 20+ 命令：40+ 秒的浏览器启动开销
- **更糟糕**：命令之间丢失所有状态

**守护进程模型的优势**：
1. **持久化状态** - 登录一次，保持登录；打开标签页，保持打开；localStorage 跨命令持久化
2. **亚秒级命令** - 首次调用后，每个命令只是 HTTP POST：~100-200ms 往返（包括 Chromium 的工作）
3. **自动生命周期** - 服务器首次使用时自动启动，空闲 30 分钟后自动关闭

### 3.2 状态文件

服务器写入 `.gstack/browse.json`（通过 tmp + rename 原子写入，模式 0o600）：

```json
{
  "pid": 12345,
  "port": 34567,
  "token": "uuid-v4",
  "startedAt": "...",
  "binaryVersion": "abc123"
}
```

**CLI 使用流程**：
1. 读取此文件以找到服务器
2. 如果文件丢失或服务器健康检查失败 → CLI 生成新服务器
3. Windows 上，基于 PID 的进程检测在 Bun 二进制中不可靠
4. **主要活性信号**：健康检查（GET /health）在所有平台上

### 3.3 端口选择

```typescript
// 10000-60000 之间的随机端口（冲突时最多重试 5 次）
const randomPort = Math.floor(Math.random() * 50000) + 10000;
```

**设计原因**：
- 10 个 Conductor 工作区可以各自运行自己的 browse 守护进程
- 零配置，零端口冲突
- 旧方法（扫描 9400-9409）在多工作区设置中经常失败

### 3.4 版本自动重启

**机制**：
1. 构建时将 `git rev-parse HEAD` 写入 `browse/dist/.version`
2. 每次 CLI 调用时，如果二进制版本与运行中服务器的 `binaryVersion` 不匹配
3. CLI 杀死旧服务器并启动新服务器

**好处**：完全防止"陈旧二进制"类的 bug - 重建二进制，下一条命令自动使用

## 四、安全模型

### 4.1 Localhost 限制

HTTP 服务器绑定到 `127.0.0.1`，而非 `0.0.0.0` - 无法从网络访问。

### 4.2 双监听器隧道架构（v1.6.0.0）

**问题**：当用户运行 `pair-agent --client` 时，守护进程启动 ngrok 隧道，使远程配对代理可以驱动浏览器。将完整守护进程表面暴露到互联网（即使在随机 ngrok 子域后面）意味着 `/health` 在任何 Origin 欺骗时泄漏根令牌，`/cookie-picker` 将令牌嵌入 HTML，任何调用者都可以获取。

**解决方案**：两个 HTTP 监听器，而非一个：

```
┌─────────────────────────────────────────────────────────────┐
│ 本地监听器（127.0.0.1:LOCAL_PORT）                           │
│ • 始终绑定                                                   │
│ • 服务引导（/health 带令牌传递）                              │
│ • /cookie-picker、/inspector/*、/welcome、/refs             │
│ • 侧边栏代理 API                                             │
│ • 完整命令表面                                               │
│ • 从不转发                                                   │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ 隧道监听器（127.0.0.1:TUNNEL_PORT）                          │
│ • 在 /tunnel/start 时惰性绑定                                │
│ • 在 /tunnel/stop 时拆除                                     │
│ • 服务锁定的允许列表：                                        │
│   - /connect（配对仪式，未认证 + 速率限制）                   │
│   - /command（仅限作用域令牌，进一步限制为浏览器驱动命令允许列表）│
│   - /sidebar-chat                                           │
│ • 其他所有端点 404                                           │
└─────────────────────────────────────────────────────────────┘
         │
         ▼
     ngrok 仅转发隧道端口
```

**安全属性**：
- 来自**物理端口分离** - 隧道调用者无法访问 `/health` 或 `/cookie-picker`，因为这些路径在该 TCP 套接字上不存在
- 头推断（检查 `x-forwarded-for`，检查 origin）不可靠（ngrok 头行为变化；本地代理可以添加这些头）
- **套接字分离是可靠的**

#### 端点映射表

| 端点 | 本地监听器 | 隧道监听器 | 注释 |
|------|----------|-----------|------|
| `/health` | ✅ 带令牌 | ❌ 404 | 引导路径 |
| `/connect` | ✅ | ✅ 速率限制 | 配对仪式 |
| `/command` | ✅ 全权限 | ✅ 作用域令牌 + 命令允许列表 | 浏览器驱动 |
| `/cookie-picker` | ✅ | ❌ 404 | 敏感 UI |
| `/inspector/*` | ✅ | ❌ 404 | 调试工具 |
| `/sidebar-chat` | ✅ | ✅ | 侧边栏代理 |

### 4.3 令牌体系

#### 根令牌（Root Token）
- 由服务器启动时生成（UUID v4）
- 存储在 `.gstack/browse.json`（0o600）
- 本地监听器的完整访问权限
- **从不通过隧道**

#### 作用域令牌（Scoped Token）
- `/connect` 配对仪式期间颁发
- 限制为浏览器驱动命令的子集（26 个命令允许列表）
- 每个配对代理一个令牌
- 可通过 `/command` 使用 `revoke-token` 撤销

#### 浏览器驱动命令允许列表（26 个命令）
```typescript
const BROWSER_DRIVING_ALLOWLIST = new Set([
  'goto', 'back', 'forward', 'reload', 'url',
  'text', 'html', 'links', 'forms', 'accessibility',
  'click', 'fill', 'select', 'hover', 'type', 'press', 'scroll', 'wait',
  'screenshot', 'tabs', 'tab', 'newtab', 'closetab',
  'snapshot', 'cookie', 'cookies'
]);
```

**排除的命令**：
- `stop` / `restart` - 不让远程代理杀死守护进程
- `cookie-import-browser` - 不暴露本地浏览器 cookie 数据库
- `eval` / `js` - 不允许任意代码执行
- CDP 原始访问 - 不绕过安全层

### 4.4 提示注入防御（侧边栏代理）

恶意网页尝试劫持侧边栏代理。GStack 提供分层防御：

```
┌─────────────────────────────────────────────────────────────┐
│ L1-L3：content-security.ts                                  │
│ • 数据标记                                                   │
│ • 隐藏元素剥离                                               │
│ • ARIA 正则表达式                                            │
│ • URL 黑名单                                                │
│ • 信封包装                                                   │
│ 位置：服务器和代理中                                         │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ L4：security-classifier.ts（TestSavantAI ONNX）            │
│ • 112MB ML 模型（本地推理）                                  │
│ • 扫描每个页面和工具输出                                      │
│ 位置：仅侧边栏代理                                           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ L4b：security-classifier.ts（Claude Haiku 记录检查）        │
│ • 对完整对话形状投票                                         │
│ 位置：仅侧边栏代理                                           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ L5：security.ts（金丝雀）                                   │
│ • 随机金丝雀令牌在系统提示中                                  │
│ • 在编译时注入，在代理中检查                                  │
│ • 检查文本、工具参数、URL、文件写入                           │
│ 位置：两者                                                   │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│ L6：security.ts（combineVerdict 集成）                      │
│ • 需要两个分类器同意才能阻止                                  │
│ • 防止单模型误报                                             │
│ 位置：两者                                                   │
└─────────────────────────────────────────────────────────────┘
```

**关键约束**：
- `security-classifier.ts` **不能**从编译的 browse 二进制导入
- `@huggingface/transformers` v4 需要 `onnxruntime-node`，在 Bun 编译的临时提取目录中 `dlopen` 失败
- 只有 `security.ts`（纯字符串操作 - 金丝雀、判决组合器、攻击日志、状态）对 `server.ts` 安全

#### 阈值

```typescript
BLOCK: 0.85       // 单层分数，如果交叉确认会导致 BLOCK
WARN: 0.60        // 交叉确认阈值。当 L4 和 L4b 都 >= 0.60 → BLOCK
LOG_ONLY: 0.40    // 记录分类器的门控（当所有层 < 0.40 时跳过 Haiku）
```

#### 集成规则
仅当 ML 内容分类器 **和** 记录分类器都报告 >= WARN 时才 BLOCK。
单层高置信度降级为 WARN - 这是 Stack Overflow 指令编写误报缓解。
**金丝雀泄漏始终 BLOCK**（确定性）。

#### 环境变量

```bash
# 紧急终止开关
GSTACK_SECURITY_OFF=1

# 选择加入 DeBERTa-v3 集成
GSTACK_SECURITY_ENSEMBLE=deberta
# 添加 ProtectAI DeBERTa-v3-base-injection-onnx 作为 L4c 分类器
# 721MB 首次运行下载
# 需要 2-of-3 ML 分类器同意（testsavant、deberta、transcript）
```

#### 文件位置

```
~/.gstack/models/testsavant-small/       # 112MB，首次运行
~/.gstack/models/deberta-v3-injection/   # 721MB，仅集成启用时
~/.gstack/security/attempts.jsonl        # 攻击日志（盐化 sha256 + 仅域名）
~/.gstack/security/device-salt           # 每设备盐（0600）
~/.gstack/security/session-state.json    # 跨进程会话状态（原子）
```

### 5.2 不受信任的内容包装

```typescript
/** 从不受信任的内容命令包装输出，带信任边界标记 */
export function wrapUntrustedContent(result: string, url: string): string {
  // 清理 URL：移除换行符以防止通过 history.pushState 注入标记
  const safeUrl = url.replace(/[\n\r]/g, '').slice(0, 200);

  // 转义内容中的标记字符串以防止边界逃逸攻击
  const safeResult = result.replace(
    /--- (BEGIN|END) UNTRUSTED EXTERNAL CONTENT/g,
    '--- $1 UNTRUSTED EXTERNAL C\u200BONTENT'
  );

  return `--- BEGIN UNTRUSTED EXTERNAL CONTENT (source: ${safeUrl}) ---
${safeResult}
--- END UNTRUSTED EXTERNAL CONTENT ---`;
}
```

**应用于命令集**：

```typescript
  'console', 'dialog', 'media', 'data', 'ux-audit',

]);
```

### 5.3 CDP（Chrome DevTools Protocol）逃生舱口

**设计哲学**：
- 精选命令覆盖 95% 的使用案例
- CDP 为罕见情况提供原始访问
- **默认拒绝**：方法必须显式添加到允许列表

```typescript
// browse/src/cdp-allowlist.ts
export const CDP_ALLOWLIST: Record<string, string> = {
  'Network.setCacheDisabled': '禁用缓存用于开发',
  'Emulation.setGeolocationOverride': '模拟地理位置',
  'Performance.getMetrics': '详细性能指标',
  // ... 仅已批准的方法
};
```

**互斥锁**：
- **浏览器范围的 CDP 调用**：与每标签页工作序列化
- **每标签页 CDP 调用**：与同一标签页上的其他工作序列化
- 防止竞态条件

**输出包装**：
- 数据导出方法的输出被包装在 UNTRUSTED 信封中
- 与页面内容命令相同的边界

## 六、浏览器集成

### 6.1 Cookie 导入

**挑战**：现代浏览器使用加密的 cookie 存储。

**解决方案**：
1. **SQLite 读取** - Bun 原生 `new Database()` 读取浏览器 cookie DB
2. **解密** - 使用系统钥匙串（macOS：Keychain Access）
3. **支持的浏览器**：
   - Chrome（所有通道：Stable、Beta、Dev、Canary）
   - Arc
   - Brave
   - Edge

```typescript
// 用法
$B cookie-import-browser chrome
$B cookie-import-browser chrome --domain github.com
```

### 6.2 GStack Browser（有头模式）

**特性**：
- 反爬虫伪装 - Google、NYTimes 等无需验证码
- 自定义品牌 - 菜单栏显示"GStack Browser"而非"Chrome for Testing"
- 侧边栏扩展内置
- 您的常规 Chrome 保持不变
- 窗口打开时浏览器保持活动 - 无空闲超时

```typescript
// 启动
$B connect          // 启动有头 Chromium
$B disconnect       // 返回无头模式
```

### 6.3 Handoff（交接）机制

**用例**：遇到 CAPTCHA、身份验证墙或 MFA 提示？

```
$B handoff
  ↓
打开可见的 Chrome，在同一页面
所有 cookie 和标签页完整无缺
  ↓
解决问题，告诉 Claude 完成
  ↓
$B resume
  ↓
代理从中断的地方继续
```

**自动建议**：代理在 3 次连续失败后自动建议交接。

### 7.3 WebSocket 认证

**约束**：浏览器无法在 WebSocket 升级时设置 `Authorization`，但**可以**通过 `new WebSocket(url, [token])` 设置 `Sec-WebSocket-Protocol`。

**流程**：
1. 扩展：`new WebSocket(url, [token])`
2. 代理读取、验证 `validTokens`
3. **必须**在升级响应中回显协议 - 否则 Chromium 立即关闭连接
4. `Set-Cookie: gstack_pty=...` 保留为非浏览器调用者的后备

### 7.4 跨窗格 PTY 注入

工具栏的 Cleanup 按钮和检查器的"发送到代码"操作都通过 `window.gstackInjectToTerminal(text)` 将文本注入到活动的 claude PTY 中，由 `sidepanel-terminal.js` 公开。

**无 `/sidebar-command` POST** - 活动 REPL 现在是侧边栏中唯一的执行表面。

### 7.5 侧边栏安全栈

**完整表格**：

| 层 | 模块 | 位置 |
|----|------|------|
| L1-L3 | `content-security.ts` | 服务器和代理 - 数据标记、隐藏元素剥离、ARIA 正则表达式、URL 黑名单、信封包装 |
| L4 | `security-classifier.ts`（TestSavantAI ONNX） | **仅侧边栏代理** |
| L4b | `security-classifier.ts`（Claude Haiku 记录） | **仅侧边栏代理** |
| L5 | `security.ts`（金丝雀） | 两者 - 在编译时注入，在代理中检查 |
| L6 | `security.ts`（combineVerdict 集成） | 两者 |

**UI 指示器**：侧边栏头部的盾牌图标显示状态（绿色/琥珀色/红色）。

## 八、技能系统

### 8.1 技能生成流程

**单一真相来源**：`.tmpl` 模板文件

```
SKILL.md.tmpl
  ↓
scripts/gen-skill-docs.ts
  ├─ resolvers/preamble.ts      # 全局序言
  ├─ resolvers/design.ts        # 设计系统知识
  ├─ resolvers/review.ts        # 审查方法论
  └─ resolvers/gbrain.ts        # GBrain 集成
  ↓
SKILL.md（生成，不要直接编辑）
```

**工作流**：
1. 编辑 `.tmpl` 文件
2. 运行 `bun run gen:skill-docs`（或 `bun run build` 自动完成）
3. 提交 `.tmpl` 和生成的 `.md` 文件

**合并冲突规则**：
- **从不**通过接受任一侧来解决生成的 SKILL.md 文件的冲突
- 相反：(1) 解决 `.tmpl` 模板的冲突，(2) 运行 `bun run gen:skill-docs` 重新生成，(3) 暂存重新生成的文件

### 8.2 令牌上限

生成的 SKILL.md 文件在超过 160KB（约 40K 令牌）时触发警告。

**设计原理**：
- 现代旗舰模型有 200K-1M 上下文窗口
- 40K 是窗口的 4-20%
- 提示缓存使更大技能的边际成本小
- **上限的目的**：捕获失控的序言/解析器增长，而非强制压缩精心调整的大技能

**合法的大技能**：
- `ship`、`plan-ceo-review`、`office-hours` 合理地打包 25-35K 令牌的行为
- 如果一个解析器在单个 PR 中添加 10K+ → 质疑它是否属于内联或作为参考文档

### 8.3 主机配置系统

**目的**：支持 10+ AI 编程代理，无需代码更改。

**流程**：
1. 添加一个 TypeScript 配置文件到 `hosts/`
2. 运行 `./setup --host <name>`
3. 完成

**示例**：`hosts/codex.ts`

```typescript
import type { HostConfig } from '../scripts/host-config';

export const codex: HostConfig = {
  name: 'codex',
  displayName: 'OpenAI Codex CLI',
  skillsDir: '~/.codex/skills',
  configFile: '~/.codex/config.yaml',
  checkCommand: 'codex --version',
  toolVariable: 'CODEX',
  // ... 适配器逻辑
};
```

**主机注册表**：`hosts/index.ts` - 导出所有，派生 Host 类型。

## 十、性能优化

### 10.1 编译的二进制文件优化

**大小**：
- `browse/dist/browse`：~58MB
- `design/dist/design`：~58MB
- 包含 Bun 运行时 + 依赖项 + 代码

**启动**：
- 编译的二进制：~1ms
- Node.js：~100ms
- **但瓶颈始终是 Chromium（~2-3s）**，而非 CLI

### 10.2 守护进程性能

**首次调用**（冷启动）：
1. 生成服务器进程：~50ms
2. 服务器启动 Chromium：~2-3s
3. 服务器准备就绪：~3s 总计

**后续调用**（热路径）：
1. CLI 读取状态文件：~1ms
2. HTTP POST 到 localhost：~5ms
3. 服务器处理：~10-20ms
4. Chromium 执行：~80-150ms
5. **总计：~100-200ms**

### 10.3 持久化状态优势

**对比冷启动**：
- 每个命令的浏览器启动：2-3s
- 20 个命令的 QA 会话：40-60s 仅浏览器启动
- **守护进程模型**：20 个命令的 QA 会话：2-4s 总计（首次 3s + 19 × 150ms）

**对比无状态**：
- Cookie 在命令之间丢失 → 每次重新认证
- 标签页在命令之间丢失 → 无法跨页面工作流
- localStorage/sessionStorage 丢失 → 无法测试有状态应用

### 11.2 升级迁移

**目的**：当更改修改磁盘状态（目录结构、配置格式、陈旧文件）时，添加迁移脚本。

**位置**：`gstack-upgrade/migrations/`

**示例**：`gstack-upgrade/migrations/001-rename-config.sh`

```bash
#!/bin/bash
# 将 ~/.gstack/config.json 重命名为 ~/.gstack/config.yaml
if [ -f ~/.gstack/config.json ]; then
  mv ~/.gstack/config.json ~/.gstack/config.yaml
fi
```

**执行**：`/gstack-upgrade` 技能在 `./setup` 期间自动运行这些。

### 11.3 版本控制

**版本格式**：`X.Y.Z.W`（major.minor.patch.micro）

**语义**：
- **MAJOR**（X+1.0.0.0）：破坏性更改
- **MINOR**（X.Y+1.0.0）：新功能、大重构
- **PATCH**（X.Y.Z+1.0）：Bug 修复、小添加
- **MICRO**（X.Y.Z.W+1）：文档、元数据

**版本碰撞协议**：
- 工作区感知 - 如果分支 A 声明 v1.7.0.0 作为 MINOR，分支 B 也是 MINOR，B 落在 v1.8.0.0（相对于主分支仍然是 MINOR）
- `bin/gstack-next-version` 在选定的碰撞级别内前进，而不是在发生碰撞时重新选择级别

## 十二、总结

GStack 的技术架构体现了三个核心设计原则：

1. **性能** - 守护进程模型 + 编译的二进制 = 亚秒级命令
2. **安全** - 分层防御（双监听器、令牌作用域、提示注入防御）
3. **可扩展性** - 主机配置系统 + 技能生成流程 = 无代码更改支持新代理

这些原则使单个开发者能够以传统团队的速度行动 - 不是通过更努力工作，而是通过使 AI 协作更快、更安全、更可靠。
