# GStack 功能结构详解

## 一、功能分层架构

GStack 的功能按照软件开发生命周期（SDLC）组织，形成一个完整的流程：

```
                    GStack 功能分层
┌────────────────────────────────────────────────────┐
│                 战略层（Think）                      │
│  /office-hours  /plan-ceo-review  /codex          │
└────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────┐
│              架构层（Plan）                          │
│  /plan-eng-review  /plan-design-review             │
│  /plan-devex-review  /autoplan                     │
└────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────┐
│              实现层（Build）                         │
│  设计实现工具  浏览器工具  代码编辑工具               │
└────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────┐
│              审查层（Review）                        │
│  /review  /investigate  /design-review             │
│  /devex-review  /cso                               │
└────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────┐
│              测试层（Test）                          │
│  /qa  /qa-only  /benchmark  /canary                │
└────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────┐
│              发布层（Ship）                          │
│  /ship  /land-and-deploy  /document-release        │
└────────────────────────────────────────────────────┘
                         ↓
┌────────────────────────────────────────────────────┐
│              反思层（Reflect）                       │
│  /retro  /learn  /benchmark-models                 │
└────────────────────────────────────────────────────┘
```

## 二、核心功能矩阵

### 2.1 按角色分类

| 角色 | 技能 | 输入 | 输出 | 时间 |
|------|------|------|------|------|
| **YC Office Hours** | `/office-hours` | 产品想法（自由文本） | 设计文档 + 强制性问题 + 实现方案 | ~10 分钟 |
| **CEO/创始人** | `/plan-ceo-review` | 设计文档或功能请求 | 战略挑战 + 4 种模式（Expansion/Selective/Hold/Reduction） | ~5 分钟 |
| **工程经理** | `/plan-eng-review` | 设计文档或功能请求 | 架构图 + 数据流 + 测试矩阵 + 失败模式 | ~10 分钟 |
| **高级设计师** | `/plan-design-review` | 设计文档或 UI mockup | 10 个维度评分（0-10）+ AI Slop 检测 + 改进建议 | ~8 分钟 |
| **DX 负责人** | `/plan-devex-review` | 产品/功能描述 | 开发者角色 + TTHW 基准 + 魔法时刻 + 摩擦点 | ~15 分钟 |
| **设计伙伴** | `/design-consultation` | 产品描述 | 完整设计系统 + 研究报告 + 创意风险 + 产品 mockup | ~20 分钟 |
| **设计探索者** | `/design-shotgun` | 视觉想法描述 | 4-6 个 AI mockup 变体 + 比较板 + 品味学习 | ~3 分钟/轮 |
| **设计工程师** | `/design-html` | Mockup（图像或描述） | 生产级 HTML/CSS + 预计算布局 + 框架检测 | ~5 分钟 |
| **资深工程师** | `/review` | Git 分支（未提交的更改） | 自动修复 + 需要确认的问题 + 完整性差距 | ~3 分钟 |
| **调试专家** | `/investigate` | Bug 报告或错误消息 | 根因分析 + 数据流跟踪 + 假设测试 + 修复（最多 3 次尝试） | ~10 分钟 |
| **设计审查员** | `/design-review` | 设计文档 + 实现的 UI | 审计报告 + 原子提交修复 + 前后截图 | ~15 分钟 |
| **DX 测试员** | `/devex-review` | 文档 URL + 入门流程 | 实际 TTHW + 截图错误 + 与计划的比较 | ~20 分钟 |
| **QA 主管** | `/qa` | Staging URL | Bug 报告 + 原子提交修复 + 回归测试 | ~10 分钟 |
| **QA 报告员** | `/qa-only` | 任何 URL | 纯 bug 报告（无代码更改） | ~5 分钟 |
| **多代理协调员** | `/pair-agent` | AI 代理选择 | 共享浏览器会话 + 作用域令牌 + 标签隔离 | ~2 分钟设置 |
| **首席安全官** | `/cso` | Git 分支（未提交的更改） | OWASP Top 10 + STRIDE + 具体利用场景 | ~8 分钟 |
| **发布工程师** | `/ship` | Git 分支（未提交的更改） | 同步主分支 + 运行测试 + 推送 + 创建 PR | ~5 分钟 |
| **发布+部署** | `/land-and-deploy` | PR URL | 合并 + 等待 CI + 部署 + 验证生产 | ~10 分钟 |
| **SRE** | `/canary` | 生产 URL | 控制台错误 + 性能回归 + 页面失败 | 持续监控 |
| **性能工程师** | `/benchmark` | URL | 页面加载时间 + Core Web Vitals + 资源大小 | ~2 分钟 |
| **技术作家** | `/document-release` | Git 分支（已提交的更改） | 更新所有项目文档（README、ARCHITECTURE 等） | ~3 分钟 |
| **工程经理** | `/retro` | 时间范围（可选） | 团队感知的每周 retro + 每人细分 + 趋势 | ~5 分钟 |
| **QA 工程师** | `/browse` | 浏览器命令 | 真实 Chromium + 真实点击 + 真实截图 | ~100ms/命令 |
| **会话管理器** | `/setup-browser-cookies` | 浏览器选择 | 导入 cookie 到无头会话 | ~1 分钟 |
| **审查管道** | `/autoplan` | 功能请求 | CEO → 设计 → eng 自动审查 + 仅品味决策 | ~20 分钟 |
| **内存** | `/learn` | 管理命令（review/search/prune/export） | 项目特定的学习管理 | ~1 分钟 |

### 2.2 按阶段分类

#### 阶段 1：思考（Think）

**目标**：在编写代码前挑战假设并重新定义问题。

| 技能 | 何时使用 | 关键输出 | 示例 |
|------|---------|---------|------|
| `/office-hours` | 产品想法的第一站 | 设计文档 + 6 个强制性问题 | "我想构建一个日历应用" → "你实际上在描述一个首席助理 AI" |
| `/plan-ceo-review` | 功能请求后 | 战略挑战 + 10 星产品愿景 | "添加导出 CSV" → "为什么不是实时 API 集成？" |
| `/codex` | 需要第二意见时 | 独立审查（OpenAI Codex CLI） | Claude 说"合并这两个"，Codex 说"保持分离" |

**流程示例**：

```
用户："我想添加一个黑暗模式切换"
  ↓
/office-hours
  ↓ 6 个强制性问题：
  - 这解决了什么痛点？
  - 谁是目标用户？
  - 为什么是现在？
  - 如果我们不构建这个会怎样？
  - 成功是什么样子？
  - 什么可能出错？
  ↓
设计文档：
  - 不仅仅是切换 - 完整的主题系统
  - 尊重系统偏好（prefers-color-scheme）
  - 记住用户选择（localStorage）
  - 跨组件一致的主题
  ↓
/plan-ceo-review
  ↓ 战略挑战：
  - 为什么是切换而非自动？
  - 主题系统是否打开更大的机会？（品牌、白标、可访问性）
  - 这是楔子还是平台？
  ↓
批准的计划 → 进入"规划"阶段
```

#### 阶段 2：规划（Plan）

**目标**：在实现前锁定架构、设计和 DX。

| 技能 | 何时使用 | 关键输出 | 示例 |
|------|---------|---------|------|
| `/plan-eng-review` | 每个非平凡功能 | ASCII 数据流图 + 状态机 + 测试矩阵 | 主题上下文提供者 + CSS 变量 + 存储同步 |
| `/plan-design-review` | 面向最终用户的 UI | 10 个维度评分 + AI Slop 检测 | "视觉层次：6/10 - 切换太微妙" |
| `/plan-devex-review` | API、CLI、SDK、文档 | 开发者角色 + TTHW 基准 + 魔法时刻 | "TTHW（Hello World）：<5 分钟 vs 竞争对手的 15 分钟" |
| `/autoplan` | 全面审查管道 | CEO → 设计 → eng 自动 | 仅表面品味决策用于批准 |

**流程示例**：

```
批准的黑暗模式计划
  ↓
/plan-eng-review
  ↓ 架构锁定：
  ┌─────────────────────────────────────┐
  │ ThemeProvider (React Context)       │
  │  ├─ useState('light'|'dark'|'auto') │
  │  ├─ useEffect(sync to localStorage) │
  │  └─ useEffect(listen prefers-color) │
  └─────────────────────────────────────┘
         ↓ CSS variables
  ┌─────────────────────────────────────┐
  │ :root[data-theme="dark"] {          │
  │   --bg: #1a1a1a;                    │
  │   --text: #e0e0e0;                  │
  │   ...                               │
  │ }                                   │
  └─────────────────────────────────────┘
  ↓ 测试矩阵：
  - 单元：ThemeProvider 状态转换
  - 集成：跨组件主题一致性
  - E2E：切换 + 刷新 + 持久性
  ↓
/plan-design-review
  ↓ 设计审计：
  - 视觉层次：6/10 → 切换更突出
  - 颜色对比：8/10 → 黑暗模式对比度增加
  - 动画：4/10 → 添加过渡（尊重 prefers-reduced-motion）
  ↓
批准的实现计划 → 进入"构建"阶段
```

#### 阶段 3：构建（Build）

**目标**：实现计划，完整性而非捷径。

| 工具类别 | 工具 | 用途 | 示例 |
|---------|------|------|------|
| **设计实现** | `/design-shotgun` | 视觉探索 | 生成 4-6 个主题选择器变体 |
|  | `/design-html` | Mockup → 代码 | 将批准的变体转换为生产 HTML/CSS |
| **浏览器自动化** | `/browse` | 浏览器操作 | 测试主题切换在真实 Chromium 中 |
|  | `/open-gstack-browser` | 有头浏览器 | 视觉 QA（查看主题在操作中） |
| **代码编辑** | `Edit` | 修改现有文件 | 添加 data-theme 属性到 <html> |
|  | `Write` | 创建新文件 | 写入 ThemeProvider.tsx |

**流程示例**：

```
批准的实现计划
  ↓
/design-shotgun "modern theme toggle button, minimal, accessible"
  ↓ 生成 6 个变体：
  [变体 1] [变体 2] [变体 3]
  [变体 4] [变体 5] [变体 6]
  ↓ 用户选择变体 3
  ↓
/design-html variant-3.png
  ↓ 生成生产代码：
  - ThemeToggle.tsx（React 组件）
  - theme-toggle.css（样式 + 过渡）
  - 可访问性（ARIA 标签、键盘导航）
  ↓
实现 ThemeProvider（根据 eng 计划）
  ↓ Claude 使用 Write/Edit 工具：
  - src/providers/ThemeProvider.tsx
  - src/hooks/useTheme.ts
  - src/styles/theme-variables.css
  ↓
集成到应用程序
  ↓
完成实现 → 进入"审查"阶段
```

#### 阶段 4：审查（Review）

**目标**：捕获通过 CI 但在生产中失败的 bug。

| 技能 | 何时使用 | 自动修复？ | 示例 |
|------|---------|----------|------|
| `/review` | 每个分支，在 `/ship` 前 | ✅ 明显的 | 竞态条件 → 询问修复 |
| `/investigate` | 遇到 bug 时 | ✅ 3 次尝试后 | "主题在刷新时闪烁" → 根因：localStorage 异步读取 |
| `/design-review` | 面向用户的 UI 更改 | ✅ 是的 | "动画太快" → 减慢到 200ms |
| `/devex-review` | API/CLI/SDK/文档更改 | ❌ 仅报告 | "TTHW 实际：8 分钟 vs 计划：5 分钟" |
| `/cso` | 安全敏感的更改 | ❌ 仅报告 | XSS 风险：用户提供的主题名称 |

**流程示例**：

```
完成实现
  ↓
/review
  ↓ 发现 3 个问题：
  [自动修复] 未使用的导入
  [自动修复] 缺少 prop 类型
  [询问] 竞态条件：如果组件在主题加载前挂载怎么办？
  ↓ 用户批准修复
  ↓
/investigate "主题在刷新时闪烁白色"
  ↓ 根因分析：
  1. 假设：CSS 未加载
     测试：检查网络标签 → CSS 已加载 ✅
  2. 假设：localStorage 读取慢
     测试：添加日志 → 读取需要 50ms ✅
  3. 假设：初始渲染使用默认主题
     测试：检查 ThemeProvider 初始状态 → 是 'light' ✅
  ↓ 修复：
  - 在初始渲染前读取 localStorage（同步）
  - 或添加加载状态（在加载时隐藏内容）
  ↓ 用户选择修复 1（同步读取）
  ↓
/design-review
  ↓ 审计发现：
  - 视觉层次：8/10 ✅
  - 动画：5/10 → 过渡太快（150ms → 200ms）[自动修复]
  - 可访问性：7/10 → 缺少焦点指示器 [自动修复]
  ↓
/cso
  ↓ 安全审计：
  - OWASP A03（注入）：⚠️  用户提供的主题名称未清理
    利用场景：主题名称 = "<script>alert('XSS')</script>"
    建议：在渲染前清理或使用允许列表
  ↓ 用户修复 XSS（添加清理）
  ↓
所有审查通过 → 进入"测试"阶段
```

#### 阶段 5：测试（Test）

**目标**：在真实浏览器中测试，生成回归测试。

| 技能 | 何时使用 | 生成测试？ | 示例 |
|------|---------|----------|------|
| `/qa` | Staging URL 准备好时 | ✅ 每个修复 | 发现"主题在 Safari 中不持久" + 修复 + 测试 |
| `/qa-only` | 生产 URL（无代码访问） | ❌ 仅报告 | "竞争对手网站" → 纯 bug 报告 |
| `/benchmark` | 每个 PR | ❌ 但记录基线 | 黑暗模式：LCP 从 1.2s → 1.3s（+8%） |
| `/canary` | 部署后 | ❌ 但持续监控 | 部署后监控 24 小时寻找回归 |

**流程示例**：

```
所有审查通过
  ↓
部署到 staging: https://staging.myapp.com
  ↓
/qa https://staging.myapp.com
  ↓ 自动化测试流程：
  1. $B goto https://staging.myapp.com
  2. $B snapshot -i
  3. 识别主题切换按钮 @e5
  4. $B click @e5
  5. $B snapshot -i
  6. 验证 data-theme="dark"
  7. $B reload
  8. $B snapshot -i
  9. 验证主题持久化
  ↓ 发现 Bug：
  "Safari：主题在刷新后重置为 light"
  ↓ 修复：
  - 调查：Safari 的 localStorage 行为
  - 根因：localStorage.setItem 在 Safari 中异步
  - 修复：等待 setItem 完成后才认为主题已更改
  ↓ 生成回归测试：
  ```typescript
  test('主题在刷新后持久化（Safari）', async () => {
    await page.goto('https://staging.myapp.com');
    await page.click('[data-testid="theme-toggle"]');
    await page.waitForFunction(() => {
      return localStorage.getItem('theme') === 'dark';
    });
    await page.reload();
    expect(await page.getAttribute('html', 'data-theme')).toBe('dark');
  });
  ```
  ↓ 重新验证修复
  ↓
/benchmark https://staging.myapp.com
  ↓ 性能基线：
  - FCP: 0.8s
  - LCP: 1.3s (+8% 由于主题系统)
  - CLS: 0.01
  - TTI: 2.1s
  ↓ 判决：可接受（< 10% 回归）
  ↓
所有测试通过 → 进入"发布"阶段
```

#### 阶段 6：发布（Ship）

**目标**：合并、部署、验证生产。

| 技能 | 何时使用 | 包括的内容 | 示例 |
|------|---------|----------|------|
| `/ship` | 分支准备好合并时 | 同步主分支 + 运行测试 + 推送 + 创建 PR | PR #42："添加黑暗模式支持" |
| `/land-and-deploy` | PR 批准后 | 合并 + 等待 CI + 部署 + 验证生产 | 合并 → Vercel 部署 → 健康检查通过 |
| `/document-release` | 合并后 | 更新所有项目文档 | README、CHANGELOG、ARCHITECTURE 同步 |

**流程示例**：

```
所有测试通过
  ↓
/ship
  ↓ 步骤：
  1. 同步 origin/main（git fetch && git merge）
  2. 解决冲突（如果有）
  3. 运行测试套件（bun test）
  4. 审计覆盖率（目标：100%）
     - 单元：ThemeProvider 100% ✅
     - 集成：跨组件 95% ⚠️  添加缺失的测试
     - E2E：用户流程 100% ✅
  5. 推送到 origin/feature/dark-mode
  6. 创建 PR（使用批准的计划中的模板）
  ↓ PR #42 创建：
  标题："添加黑暗模式支持"
  主体：
  - 摘要：根据 CEO 计划实现的完整主题系统
  - 测试计划：单元 + 集成 + E2E + Safari 特定
  - 截图：浅色/深色模式并排
  ↓ PR 批准（人类审查者）
  ↓
/land-and-deploy PR #42
  ↓ 步骤：
  1. 合并到 main（gh pr merge --squash）
  2. 等待 CI 通过（GitHub Actions）
     - Lint: ✅
     - Type check: ✅
     - Unit tests: ✅
     - E2E tests: ✅
  3. 等待部署完成（Vercel）
     - 部署 URL: https://myapp.com
     - 状态：生产就绪 ✅
  4. 运行健康检查
     - GET /: 200 ✅
     - GET /api/health: 200 ✅
  5. 验证功能
     - $B goto https://myapp.com
     - $B click [data-testid="theme-toggle"]
     - $B snapshot -i
     - 验证 data-theme="dark" ✅
  ↓ 部署成功
  ↓
/document-release
  ↓ 更新文档：
  - README.md："现在支持浅色和深色主题"
  - CHANGELOG.md："v1.5.0.0：添加黑暗模式支持"
  - ARCHITECTURE.md：添加主题系统图表
  ↓ 提交文档更改
  ↓
功能发布完成 → 进入"反思"阶段
```

#### 阶段 7：反思（Reflect）

**目标**：学习、监控、改进。

| 技能 | 何时使用 | 输出 | 示例 |
|------|---------|------|------|
| `/retro` | 每周（或每个 sprint 后） | 团队细分 + 发布趋势 + 增长机会 | "本周：3 个功能、12 个 bug 修复、5 个 PR" |
| `/learn` | 持续（随着发现模式） | 项目特定的学习 | "Safari localStorage 是异步的" |
| `/canary` | 部署后 24-48 小时 | 控制台错误 + 性能回归 + 用户报告 | "黑暗模式：无回归 ✅" |
| `/benchmark-models` | 当优化提示/工作流程时 | 跨模型比较（Claude/GPT/Gemini） | "Claude Opus：最佳设计审查，GPT-4：更快实现" |

**流程示例**：

```
功能发布完成
  ↓
/canary https://myapp.com
  ↓ 部署后监控（24 小时）：
  - 控制台错误：0 ✅
  - 性能回归：
    - LCP: 1.3s vs 基线 1.2s (+8%)
    - 无异常峰值 ✅
  - 页面失败：0 ✅
  - 用户报告：1 个反馈（"喜欢黑暗模式！"）
  ↓ 判决：生产健康
  ↓
/retro

### 4.5 安全层

**提示注入防御**（侧边栏代理）：

```
恶意页面尝试劫持代理
  ↓
页面内容通过安全层：
  ├─ L1-L3: content-security.ts
  │    ├─ 数据标记
  │    ├─ 隐藏元素剥离
  │    ├─ ARIA 正则表达式（"ignore previous"）
  │    ├─ URL 黑名单
  │    └─ 信封包装
  ├─ L4: security-classifier.ts（ML）
  │    ├─ TestSavantAI ONNX（112MB，本地）
  │    └─ 扫描页面 + 工具输出
  ├─ L4b: security-classifier.ts（记录）
  │    ├─ Claude Haiku 记录检查
  │    └─ 对完整对话形状投票
  ├─ L5: security.ts（金丝雀）
  │    ├─ 随机令牌在系统提示中
  │    └─ 检查文本、工具参数、URL、文件写入
  └─ L6: security.ts（判决）
       ├─ combineVerdict（需要 2-of-2 同意）
       └─ BLOCK / WARN / SAFE
            ↓
如果 BLOCK：
  - 侧边栏显示盾牌图标（红色）
  - 阻止操作
  - 记录尝试到 ~/.gstack/security/attempts.jsonl
            ↓
如果 WARN：
  - 侧边栏显示盾牌图标（琥珀色）
  - 允许操作但记录
            ↓
如果 SAFE：
  - 侧边栏显示盾牌图标（绿色）
  - 正常继续
```

**环境变量**：
- `GSTACK_SECURITY_OFF=1` - 紧急终止开关
- `GSTACK_SECURITY_ENSEMBLE=deberta` - 选择加入 DeBERTa-v3（721MB，2-of-3 同意）

### 4.6 持续检查点模式

**配置**：
```bash
gstack-config set checkpoint_mode continuous
gstack-config set checkpoint_push false  # 本地仅（默认）
```

**行为**：

```
技能开始工作
  ↓
每 N 分钟或每个主要步骤：
  git add -A
  git commit -m "WIP: [步骤描述]

  [gstack-context]
  decisions: [做出的决策]
  remaining: [剩余工作]
  failed: [失败的方法]
  "
  ↓ 如果 checkpoint_push=true
  git push origin HEAD
  ↓ 否则保留本地
  ↓
崩溃 / 上下文切换
  ↓
/context-restore
  ↓ 读取最新 WIP 提交
  ↓ 提取 [gstack-context]
  ↓ 重构会话状态：
  - "你正在实现 X"
  - "你已经完成 Y 和 Z"
  - "你尝试 A 但失败了，因为 B"
  - "剩余：C、D、E"
  ↓
从中断的地方继续
  ↓
完成工作
  ↓
/ship
  ↓ Filter-squash WIP 提交：
  - 保留非 WIP 提交
  - 将所有 WIP 压缩为一个干净的提交
  - 删除 [gstack-context]（仅内部）
  ↓
干净的 git 历史用于 PR
```

**好处**：
- 生存崩溃和上下文切换
- 无需从头开始重复工作
- bisect 保持干净（WIP 在 `/ship` 时压缩）

## 六、总结

GStack 的功能结构体现了三个核心设计原则：

1. **完整的 SDLC** - 覆盖从思考到反思的每个阶段
2. **流程优先** - 每个技能都知道何时停止并传递给下一个
3. **AI 原生** - 不是人类工作流程的 AI 辅助，而是为 AI 协作从头设计的工作流程

这些原则使单个建造者能够以传统团队的速度行动 - 不是通过更努力工作，而是通过正确的工具、正确的流程和正确的自动化。

**关键数字**：
- **23+ 专家角色** - 覆盖完整的工程团队
- **100+ 浏览器命令** - 亚秒级延迟，持久化状态
- **3-100x 压缩比** - AI vs 人类团队时间
- **10-15 并行 sprint** - 使用 Conductor 的实际最大值

这不是未来的承诺 - 这是现在正在发生的现实。
