# 14 如何评测

## gstack 的三层评测体系

gstack 拥有最接近工业级水准的 Skills 评测体系，三层测试金字塔覆盖从静态验证到全流程 E2E。

---

## 14.1 测试金字塔总览

```
        ┌─────────────────────────────────────┐
        │    Tier 3: E2E (~$3.85/run)         │
        │    claude -p 全流程执行 + LLM judge  │  ← 最贵，最真实
        └─────────────────────────────────────┘
              ┌───────────────────────────┐
              │  Tier 2: LLM Judge        │
              │  (~$0.15/run)             │  ← 中等成本
              │  SKILL.md 文档质量评估    │
              └───────────────────────────┘
                    ┌───────────────┐
                    │ Tier 1: 静态  │
                    │ (免费, <2s)   │  ← 最快，CI 必须
                    │ schema + lint │
                    └───────────────┘
```

## 14.2 Tier 1: 静态验证

**命令:** `bun test`

**文件:** `test/skill-validation.test.ts`, `test/gen-skill-docs.test.ts`

**验证内容:**
- SKILL.md.tmpl 必须有有效 frontmatter
- `name` 字段必须匹配目录名
- `allowed-tools` 必须是已知工具的子集
- `description` 不超过 token 上限
- `gen-skill-docs` 生成的 SKILL.md 无模板残留（`{{PLACEHOLDER}}` 未替换）
- Browse integration tests（`browse/test/`）

**运行时机:** 每次提交前（`bun test` 是免费、<2s 的 pre-commit 检查）

---

## 14.3 Tier 2: LLM Judge

**命令:** `bun run test:evals`

**文件:** `test/skill-llm-eval.test.ts`

**机制:**
```typescript
// test/helpers/llm-judge.ts
const scores = await judge(
  'Evaluate this SKILL.md documentation quality',
  skillContent
);
// 返回: {clarity: 1-5, completeness: 1-5, actionability: 1-5}
```

**Judge 模型:** `claude-sonnet-4-6`

**退出条件:** 任一维度 < 3 → 测试失败

**评分维度:**
| 维度 | 含义 |
|------|------|
| clarity | 指令是否清晰，Claude 能理解 |
| completeness | 是否涵盖所有关键步骤 |
| actionability | Claude 能否直接按指令执行 |

---

## 14.4 Tier 3: E2E 全流程测试

**命令:** `bun run test:evals` (包含 E2E)

**文件:** `test/skill-e2e-*.test.ts`

**核心机制:**

```typescript
// test/helpers/session-runner.ts
const result = await runSkillTest({
  prompt: 'Read qa-SKILL-section.md and test https://...',
  workingDirectory: dir,
  maxTurns: 15,
  allowedTools: ['Bash', 'Read', 'Write'],
  testName: 'qa-bug-detection',
});
// 实际运行: claude -p --model claude-sonnet-4-6 --output-format stream-json
```

**Diff-based 测试选择:**
```
git diff origin/main...HEAD
    ↓ 分析改动文件
    ↓ 查询 E2E_TOUCHFILES 依赖映射
    ↓ 只运行受影响的测试
```

**两层分类系统:**

| 层级 | 描述 | 运行时机 | 成本 |
|------|------|---------|------|
| `gate` | 安全守护 + 确定性功能 | CI（每个 PR） | ~$0.5-1/run |
| `periodic` | 质量基准 + 非确定性 + 外部服务 | 每周 cron / 手动 | ~$3/run |

**分类标准:**
- 安全守护测试 → `gate`
- 确定性功能测试 → `gate`
- 质量基准测试 → `periodic`
- Opus 模型测试 → `periodic`
- 需要外部服务（Codex, Gemini）→ `periodic`

## 14.5 特殊评测类型

### planted-bug 检测评测

```
test/fixtures/qa-eval.html (植入已知 bug)
    ↓ claude -p 运行 /qa 指令片段
    ↓ 对比 test/fixtures/qa-eval-ground-truth.json
    ↓ 计算:
        检测率 = detected / total
        漏报率 = missed / total
        误报率 = false_positives / total
```

### judgePosture (模式行为回归)

```
office-hours expansion mode 输出
    ↓ judge 评估:
        axis_a (surface_framing): 1-5
        axis_b (decision_preservation): 1-5
    ↓ 检测 V1 写作风格是否破坏了模式特定的能量
```

### Real-PTY E2E (AskUserQuestion 渲染验证)

```
test/helpers/claude-pty-runner.ts
    ↓ Bun.spawn({terminal: true}) 真实 PTY
    ↓ 通过 stdin/stdout 驱动 claude
    ↓ 解析 ANSI 转义后的渲染文本
    ↓ 验证 plan-mode AskUserQuestion 渲染正确
       (工具路径不可见，直接终端渲染)
```

## 14.6 评测结果持久化

```
~/.gstack/projects/{slug}/evals/
    ├── {version}-{branch}-{tier}-{timestamp}.json   ← 每次运行结果
    ├── {version}-{branch}-{tier}-{timestamp}.json
    └── ...

eval:compare  → 自动对比最近两次运行
eval:summary  → 跨所有运行的聚合统计
eval:list     → 列出所有历史评测
```

**EvalCollector 结构:**
```typescript
interface EvalEntry {
  testName: string;
  passed: boolean;
  scores?: JudgeScores;
  turns: number;
  cost: number;
  model: string;
  timestamp: string;
  transcript: Message[];
}
```

## 14.7 与其他项目的评测体系对比

| 维度 | gstack | deer-flow | hermes-agent | nanobot |
|------|--------|-----------|--------------|---------|
| **评测框架** | bun test + LLM judge + claude -p | pytest 组件测试 | Atropos RL + Terminal-Bench 2 | pytest（少量） |
| **评测类型** | 技能行为 + 文档质量 | 组件正确性 | 任务完成率（pass/fail）| 代码正确性 |
| **测试规模** | ~40-50 测试（含 E2E） | 130+ 文件 | ~3000 个 pytest 用例 | 少量 |
| **benchmark 数据集** | 自建 planted-bug fixtures | 无 | Terminal-Bench 2 | 无 |
| **eval 环境隔离** | os.tmpdir() 临时目录 | Docker/本地沙箱 | Modal 沙箱（远程）| 无 |
| **并发评测** | ✅ (asyncio.gather 100并行) | 无 | ✅ (tool_pool_size=128) | 无 |
| **RL 集成** | ❌ | ❌ | ✅ (Atropos GRPO/PPO) | ❌ |
| **历史追踪** | ✅ (JSON 持久化 + 自动对比) | ❌ | ✅ (WandB) | ❌ |
| **成本控制** | ✅ (diff-based 选择) | ❌ | ✅ (TBLite 轻量版) | ❌ |

## 14.8 评测理念

**gstack（评测即守护）:**
- 测试保护用户体验质量，而非模型训练
- diff-based 选择确保只测试被改动影响的技能
- gate 测试阻止回退，periodic 测试衡量质量改善
- 评测结果持久化，支持历史趋势分析

**成本意识设计:**
- Tier 1（免费）→ 每次提交前
- Tier 2（$0.15）→ PR 时
- Tier 3 gate（$0.5-1）→ CI
- Tier 3 periodic（$3）→ 每周

最大化信号密度，最小化 API 成本。
