# GStack 产品概述

## 一、产品定位

GStack 是一个**将 Claude Code 转化为虚拟工程团队的开源软件工厂**，由 Y Combinator 总裁兼 CEO Garry Tan 开发并开源。

### 核心价值主张

> "将单个开发者的生产力提升到传统 20 人团队的水平"

GStack 的核心理念是：**AI 辅助编程使完整性的边际成本接近于零**。在传统开发中需要数天甚至数周的工作，使用 GStack 可以压缩到数小时甚至数分钟。

### 目标用户

1. **创始人和 CEO** - 特别是仍然希望亲自编码的技术创始人
2. **Claude Code 新用户** - 提供结构化的角色而不是空白提示
3. **技术负责人和资深工程师** - 为每个 PR 提供严格的审查、QA 和发布自动化

## 二、产品核心特性

### 2.1 虚拟团队成员（23+ 专家角色）

GStack 将 AI 能力具象化为不同的专家角色，每个角色对应一个 slash 命令：

| 专家角色 | Slash 命令 | 职责 |
|---------|-----------|------|
| **YC Office Hours** | `/office-hours` | 产品策略顾问 - 6 个强制性问题重新定义产品 |
| **CEO/创始人** | `/plan-ceo-review` | 战略思考 - 找出隐藏在需求中的 10 星产品 |
| **工程经理** | `/plan-eng-review` | 架构锁定 - 数据流、边缘情况和测试计划 |
| **高级设计师** | `/plan-design-review` | 设计审查 - 0-10 分评分，AI Slop 检测 |
| **资深工程师** | `/review` | 代码审查 - 找出通过 CI 但在生产环境会崩溃的 bug |
| **QA 主管** | `/qa` | 测试应用 - 真实浏览器操作，自动生成回归测试 |
| **发布工程师** | `/ship` | 发布管理 - 同步主分支、运行测试、推送、创建 PR |
| **调试专家** | `/investigate` | 系统化根因分析 - 铁律：不调查不修复 |
| **首席安全官** | `/cso` | OWASP Top 10 + STRIDE 威胁建模 |

### 2.2 完整的开发流程

GStack 不仅是工具集合，更是一个**结构化的流程**：

```
思考 → 计划 → 构建 → 审查 → 测试 → 发布 → 反思
  ↓      ↓      ↓      ↓      ↓      ↓      ↓
office  plan   build  review  qa    ship   retro
hours   -ceo
```

每个技能都会将结果传递给下一个环节：
- `/office-hours` 写入设计文档 → `/plan-ceo-review` 读取
- `/plan-eng-review` 写入测试计划 → `/qa` 执行
- `/review` 发现 bug → `/ship` 验证已修复

### 2.3 浏览器自动化（核心技术优势）

**GStack Browser** - 配备 AI 控制的 Chromium：

- **亚秒级延迟** - 守护进程模式，首次启动 ~3 秒，后续命令 ~100-200ms
- **持久化状态** - 登录状态、Cookie、标签页跨命令保持
- **真实浏览器** - 反爬虫伪装，Google/NYTimes 等网站无需验证码
- **侧边栏 Agent** - Chrome 侧边栏中的自然语言浏览器助手
- **100+ 命令** - 从导航、读取、交互到数据提取的完整命令集

技术亮点：
```typescript
// 架构：CLI → HTTP → 服务器 → CDP → Chromium
$B snapshot -i  // AI 代理调用
  ↓ HTTP POST localhost:PORT
  ↓ 服务器分发命令
  ↓ Chrome DevTools Protocol
  ↓ Chromium 执行并返回
```

### 2.4 AI 协同（跨模型第二意见）

- **`/codex`** - OpenAI Codex CLI 独立审查
- **`/pair-agent`** - 多 AI 代理共享浏览器（OpenClaw、Hermes、Cursor 等）
- **跨模型分析** - 当 Claude 和 OpenAI 都审查同一分支时，显示交叉对比

## 四、技术哲学

### 4.1 三大核心原则（ETHOS.md）

#### 1. **Boil the Lake（煮干湖泊）**
AI 辅助编程使完整性的成本接近零。当完整实现只比捷径多几分钟时，**总是做完整的事情**。

- ✅ **湖泊**（可煮干）：100% 测试覆盖率、完整功能实现、所有边缘情况
- ❌ **海洋**（不可煮干）：从头重写整个系统、多季度平台迁移

#### 2. **Search Before Building（先搜索再构建）**
在构建任何涉及不熟悉模式的东西之前，先搜索是否已有解决方案。

**知识的三层结构**：
- **Layer 1**：久经考验的标准模式（但偶尔质疑才能产生突破）
- **Layer 2**：新兴流行的最佳实践（需要审慎评估，人群可能错误）
- **Layer 3**：第一性原理推理（最有价值，优先于一切）

#### 3. **User Sovereignty（用户主权）**
AI 模型推荐，用户决策。这是覆盖所有其他规则的唯一规则。

- 即使 Claude 和 Codex 都建议合并两个东西，如果用户说"不，保持分离"，用户永远是对的
- 遵循 Karpathy 的"钢铁侠战衣"哲学：伟大的 AI 产品是增强用户，而非替代用户

### 4.2 完整性原则

**测试一切** - `/ship` 从零开始引导测试框架（如果项目没有的话）：
- 每次 `/ship` 运行产生覆盖率审计
- 每个 `/qa` bug 修复生成回归测试
- 目标是 100% 测试覆盖率

**文档自动更新** - `/document-release` 自动保持文档同步：
- 读取项目中的每个文档文件
- 与 diff 交叉引用
- 更新所有漂移的内容（README、ARCHITECTURE、CLAUDE.md 等）

## 五、使用场景

### 5.1 典型工作流示例

```
你：     我想构建一个日历日报应用
你：     /office-hours
Claude： [询问痛点 - 具体例子，而非假设]

你：     多个 Google 日历，事件信息陈旧，位置错误...
Claude： 我要挑战你的框架。你说"日报应用"，但你实际描述的
        是一个个人首席助理 AI。
        [提取你未意识到的 5 个能力]
        [挑战 4 个前提 - 你同意、不同意或调整]
        [生成 3 种实现方案及工作量估算]
        建议：明天发布最窄的楔子，从实际使用中学习...

你：     /plan-ceo-review
        [读取设计文档，挑战范围，运行 10 节审查]

你：     /plan-eng-review
        [数据流 ASCII 图、状态机、错误路径]
        [测试矩阵、失败模式、安全考虑]

你：     批准计划。退出计划模式。
        [在 11 个文件中写入 2,400 行代码。约 8 分钟]

你：     /review
        [自动修复] 2 个问题。[询问] 竞态条件 → 你批准修复

你：     /qa https://staging.myapp.com
        [打开真实浏览器，点击流程，发现并修复 bug]

你：     /ship
        测试：42 → 51（+9 新增）。PR: github.com/you/app/pull/42
```

### 5.2 并行 Sprint

使用 [Conductor](https://conductor.build) 运行多个 Claude Code 会话：
- 10-15 个并行 sprint 是当前实际最大值
- 一个会话运行 `/office-hours`（新想法）
- 另一个运行 `/review`（PR）
- 第三个实现功能
- 第四个在 staging 上运行 `/qa`
- 六个在其他分支上工作

**Sprint 结构使并行性可行** - 没有流程，10 个 agent 就是 10 个混乱源。有了流程，每个 agent 都确切知道要做什么以及何时停止。

## 六、安装与部署

### 6.1 快速安装（30 秒）

**前置要求**：
- [Claude Code](https://docs.anthropic.com/en/docs/claude-code)
- [Git](https://git-scm.com/)
- [Bun](https://bun.sh/) v1.0+
- [Node.js](https://nodejs.org/)（仅 Windows）

**Step 1**：安装到机器
```bash
git clone --single-branch --depth 1 https://github.com/garrytan/gstack.git ~/.claude/skills/gstack
cd ~/.claude/skills/gstack
./setup
```

**Step 2**：团队模式（推荐，自动更新）
```bash
(cd ~/.claude/skills/gstack && ./setup --team) && \
~/.claude/skills/gstack/bin/gstack-team-init required && \
git add .claude/ CLAUDE.md && \
git commit -m "require gstack for AI-assisted work"
```

## 九、与竞品对比

### 9.1 vs GitHub Copilot
- **Copilot**：行级代码补全 + 聊天
- **GStack**：端到端工作流 + 23 个专家角色 + 浏览器自动化

### 9.2 vs Cursor
- **Cursor**：IDE 内 AI 编程助手
- **GStack**：完整的虚拟工程团队，从产品思考到 QA 到发布

### 9.3 vs Andrej Karpathy 规则集
Karpathy 的 [AI coding rules](https://github.com/forrestchang/andrej-karpathy-skills)（17K stars）确定了 4 种失败模式：
- 错误假设
- 过度复杂
- 正交编辑
- 命令式优于声明式

**GStack 的工作流技能强制执行所有四项**：
- `/office-hours` 在编写代码前将假设显式化
- 混淆协议阻止 Claude 在架构决策上猜测
- `/review` 捕获不必要的复杂性和驾车式编辑
- `/ship` 将任务转换为可验证的目标，测试优先执行
