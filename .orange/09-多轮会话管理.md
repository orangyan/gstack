# 09 多轮会话管理

## gstack 的会话管理

gstack 没有传统意义上的"会话持久化"——每个技能调用是独立的 `claude -p` 进程，没有跨进程的持久化上下文。

---

## 9.1 gstack 的多层"会话"概念

| 组件 | 机制 | 存储 | 生命周期 |
|------|------|------|---------|
| **浏览器会话** | browse.json (pid+port+token) | `~/.gstack/browse.json` | 进程级，守护进程重启时重新生成 |
| **Claude 会话** | Claude Code 原生会话 | Claude Code 管理 | 用户主动关闭 |
| **Eval 会话** | JSON 文件 | `~/.gstack/projects/{slug}/evals/` | 持久，无限期 |
| **安全会话** | SSE cookie (30 min) + PTY cookie | 服务器内存 | 30 分钟 TTL |
| **活跃标记** | `~/.gstack/sessions/$PPID` | 文件系统 | 120 分钟后自动清理 |

---

## 9.2 上下文恢复机制（持续检查点模式）

gstack 通过 git commits 实现跨会话状态保存：

```bash
# 每个主要步骤自动创建 WIP 提交
git commit -m "WIP: [步骤描述]

[gstack-context]
decisions: [做出的决策]
remaining: [剩余工作]
failed: [失败的方法]
"
```

**恢复时：**
```
/context-restore
    ↓ 读取最新 WIP 提交
    ↓ 提取 [gstack-context] 元数据
    ↓ 重构会话状态：
      - "你正在实现 X"
      - "你已经完成 Y 和 Z"
      - "你尝试 A 但失败了，因为 B"
      - "剩余：C、D、E"
```

**发布时 (/ship)：** Filter-squash WIP 提交 → 干净的 git 历史

---

## 9.3 会话感知 Preamble

每次技能启动时，Preamble 统计活跃会话数：

```bash
_SESSIONS=$(ls ~/.gstack/sessions/ 2>/dev/null | wc -l | xargs)
```

Claude 用这个信息理解并发使用情况（是否有其他会话正在工作），从而调整行为。

---

## 9.4 与其他项目的会话管理对比

| 维度 | gstack | deer-flow | hermes-agent | nanobot |
|------|--------|-----------|--------------|---------|
| **持久化机制** | git WIP commits | LangGraph Checkpointer | SQLite WAL | JSON 文件 |
| **存储层** | Git 对象存储 | PostgreSQL / InMemory | SQLite | 本地文件 |
| **会话 ID** | PPID (进程 ID) | thread_id (UUID) | session_id | session_file |
| **跨进程** | ✅ (git) | ✅ (数据库) | ✅ (SQLite) | ✅ (文件) |
| **断点恢复** | ✅ (/context-restore) | ✅ (自动) | ✅ (自动) | ❌ |
| **历史搜索** | ❌ | ❌ | ✅ (FTS5) | ❌ |
| **并发会话** | ✅ (多 claude -p 进程) | ⚠️ (有锁) | ✅ | ✅ |

---

## 9.5 gstack 的无状态设计哲学

gstack 采用**无状态技能调用**：
- 每个 `/ship`、`/qa`、`/review` 是独立的 `claude -p` 会话
- 技能之间通过**文件**（git、SKILL.md、learnings.jsonl）而非内存传递状态
- 这使得多个技能可以**并行运行**（Conductor 10-15 个并行会话）
- 崩溃时无状态丢失风险（状态在文件系统，不在内存）

这与 deer-flow（LangGraph 持久状态机）和 hermes-agent（SQLite 持久会话）形成鲜明对比。
